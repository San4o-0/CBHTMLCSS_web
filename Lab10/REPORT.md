## 1. Дослідницькі завдання (§4)

### 4.1. Console і типи помилок

| Код у Console                       | Повідомлення                                                                           | Stack Trace         |
| ----------------------------------- | -------------------------------------------------------------------------------------- | ------------------- |
| `notDefinedVariable`                | `Uncaught ReferenceError: notDefinedVariable is not defined`                           | `at <anonymous>:1:1` |
| `null.length`                       | `Uncaught TypeError: Cannot read properties of null (reading 'length')`                | `at <anonymous>:1:6` |
| `let x = ;`                         | `Uncaught SyntaxError: Unexpected token ';'`                                           | **немає**           |
| `Promise.reject(new Error('test'))` | `Uncaught (in promise) Error: test`                                                    | `at <anonymous>:1:16` |
| `JSON.parse('{')`                   | `Uncaught SyntaxError: Expected property name or '}' in JSON at position 1 (line 1 column 2)` | `at <anonymous>:1:6` |

**Висновки.** Спільне — префікс `Uncaught`: виняток ніхто не перехопив. `ReferenceError` —
звернення до імені, якого немає в жодній області видимості; `TypeError` — значення є, але не того
типу (властивість у `null`/`undefined`, виклик не-функції). `SyntaxError` у коді виникає на етапі
**розбору**, до виконання, тому стеку немає — жоден рядок скрипта не виконався; необроблений
`TypeError` під час виконання перериває лише поточне завдання (обробник, callback), а сторінка
працює далі. `JSON.parse('{')` — теж `SyntaxError`, але він кидається **під час виконання**
функцією `JSON.parse`, тому стек є. `Uncaught (in promise)` — відхилений Promise, якому ніхто не
додав `.catch()`. Логічні дефекти (неправильний селектор, хибний порядок) у Console не потрапляють
зовсім. Перша помилка зазвичай найважливіша: наступні часто є її наслідком (код далі працює з
неповним станом). Preserve log зберігає записи після перезавантаження сторінки.

### 4.2. Stack Trace і панель Sources

```text
Uncaught TypeError: Cannot read properties of undefined (reading 'name')
    at c (<anonymous>:1:52)
    at b (<anonymous>:2:23)
    at a (<anonymous>:3:23)
    --- setTimeout (async) ---
    at <anonymous>:4:1
```

З Pause on uncaught exceptions Sources зупиняється на рядку в `c()` і показує те, чого немає в
Console: **Scope → Local: `user = undefined`**, Call Stack `c ← b ← a ← setTimeout (async) ←
(anonymous)`, можна покроково виконувати й додавати вирази у Watch.

**Висновки.** Стек читається згори донизу: верхній кадр — де виняток кинуто, нижчі — хто
викликав. Кожен кадр — функція, файл, рядок і колонка. Рядок `setTimeout (async)` позначає
асинхронну частину: DevTools запам'ятовує стек у момент постановки callback-а в чергу й
«приклеює» його до стеку виконання. **Верхній рядок — місце виявлення, а не обов'язково причина**:
у сценарії A помилка виявляється в `format.js:5`, а причина — в `data/venues.json` (див. §2).
Типи breakpoints: line-of-code, conditional, logpoint (лише логує), DOM change, event listener,
exception (uncaught / caught).

### 4.3. DOM у DevTools

На кнопці «Забронювати» першої картки: вкладка **Event Listeners** — `click` →
`js/main.js:60`; у Console `getEventListeners($0)` — `click: 1 (useCapture = false)`. Результати
збігаються: обидва способи читають той самий список обробників вузла.

**Висновки.** Elements показує **поточний** DOM — після того, як JavaScript його змінив; HTML-файл
і View page source — лише те, що прийшло з сервера (у Courtly там порожній `#results`). `$0` —
виділений елемент, `$()` / `$$()` — скорочення `querySelector` / `querySelectorAll`,
`monitorEvents()` логує події елемента. `querySelector` і `getElementById` повертають `null`,
`querySelectorAll` — порожній static `NodeList`; `getElementsBy…` і `children` — live-колекції.
Обробник прив'язаний до **вузла**, а не до селектора: якщо вузол замінити (наприклад, через
`innerHTML`), новий вузол обробника не має — це причина дефекту B.2. Event delegation (обробник на
контейнері) цієї проблеми не має.

### 4.4. Event Loop

```js
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
queueMicrotask(() => console.log('4'));
(async () => { console.log('5'); await null; console.log('6'); })();
console.log('7');
```

| Мій прогноз            | Прогноз AI (до запуску) | Фактично                |
| ---------------------- | ----------------------- | ----------------------- |
| `1, 5, 7, 3, 4, 2, 6`  | `1, 5, 7, 3, 4, 6, 2`   | `1, 5, 7, 3, 4, 6, 2`   |

**Де мій прогноз хибний:** я вважав, що продовження після `await` виконається після таймера. Насправді
`await null` ставить продовження в **microtask queue**, як і `.then()`, а `setTimeout` — у **task
queue**.

**Пояснення.** Синхронно (Call Stack): `1`; `setTimeout` передає callback Web API таймера, той
після 0 мс ставить його в task queue; `.then` і `queueMicrotask` ставлять callback-и в microtask
queue (3, потім 4); async-функція виконується **синхронно до першого `await`** — друкує `5` і
повертає pending Promise; `await null` ставить продовження в microtask queue (6); далі `7`. Скрипт
завершився, Call Stack порожній → Event Loop **повністю** спорожнює microtask queue: `3, 4, 6`
(мікрозадачі, додані під час цього, теж виконуються одразу). Потім можливий рендеринг, і лише
потім наступний task — `2`. «0 мс» — це мінімальна затримка до постановки в чергу, а не «одразу».

### 4.5. AI-assisted debugging

AI реально допомагає: швидко розбирає повідомлення й стек, пропонує кілька конкурентних гіпотез,
знаходить пов'язаний код (наприклад, що `renderBookingsCount` ніде не оголошено, а є
`renderBookingCount`), формулює мінімальний patch і чек-лист регресії. Слабкі місця: тенденція
лагодити симптом там, де помилка виявилася (`value ?? 0` у `formatPrice`), пропонувати
`try/catch`, `?.`, `setTimeout` «із запасом», а також «бачити» причини, яких немає в доказах. Тому
кожну гіпотезу AI тут підтверджено або відкинуто доказом з DevTools (див. таблиці гіпотез нижче).

**Кроки відтворення:** відкрити сторінку → Місто «Усі міста», Вид спорту «Усі види» → «Знайти».
Так само — будь-який пошук, у результатах якого є Royal Court (Львів + Теніс, Усі міста + Теніс…).

## 3. Сценарій B — DOM

### B.1. Кнопка меню не працює, а «Мої бронювання» відкриває меню

**Очікувано (§3.1):** на ширині < 1024 px кнопка меню відкриває/закриває навігацію, її
`aria-expanded` відповідає стану. **Фактично:** клік по кнопці меню нічого не робить; клік по
«Мої бронювання» відкриває діалог **і** навігацію, а `aria-expanded="true"` з'являється на кнопці
«Мої бронювання». У Console — жодної помилки.

**Докази з DevTools:**

| Перевірка                                                  | Результат                                                    |
| ---------------------------------------------------------- | ------------------------------------------------------------ |
| `document.querySelector('.site-header button').className` | `"button button--outline bookings-toggle"` — **не** меню     |
| `getEventListeners($('.menu-toggle'))`                     | `{}` — обробників немає                                      |
| `getEventListeners($('.bookings-toggle'))`                 | `click: 2` — свій обробник + обробник меню                   |
| Після кліку «Меню»: `.menu-toggle[aria-expanded]`          | `"false"`, `#site-nav.is-open` — немає                        |
| Після кліку «Мої бронювання»: `.bookings-toggle[aria-expanded]` | `"true"`, `#site-nav.is-open` — є                      |

**Розбіжність:** код очікує, що `.site-header button` — кнопка меню, а в DOM першою кнопкою в
header іде «Мої бронювання» (кнопка меню — друга).

**Prompt AI:** «Кнопка меню на < 1024 px не реагує, а "Мої бронювання" відкриває навігацію.
Console порожня. Нижче — код mobile menu з main.js, розмітка header і результати
`getEventListeners` для обох кнопок. Назви можливі причини й перевірки. Код не змінюй».
**Відповідь AI (стисло):** «Селектор `.site-header button` повертає першу кнопку header —
`.bookings-toggle`, тому обробник меню висить на ній. Перевірте `$('.site-header button')` у
Console. Альтернатива — CSS ховає меню навіть з `.is-open`: відкидається тим, що `is-open` на
`#site-nav` не з'являється після кліку по кнопці меню».

**Виправлення:** [`26a2c38`](https://github.com/San4o-0/CBHTMLCSS_web/commit/26a2c38) — селектор
`.menu-toggle`. **Після:** `.menu-toggle` має `click: 1`, `.bookings-toggle` — `click: 1`; клік по
меню → `aria-expanded="true"`, навігація видима; повторний клік → `"false"`, закрито; «Мої
бронювання» більше не чіпає меню. На ≥ 1024 px кнопку меню приховано (`display: none`).

### B.2. «Забронювати» не працює після пошуку

**Очікувано (§3.4):** «Забронювати» на **будь-якій** картці на екрані відкриває діалог саме цього
майданчика. **Фактично:** на старті працює, а після будь-якого пошуку — ні; помилок немає.

| Перевірка                                                   | Результат                                      |
| ----------------------------------------------------------- | ---------------------------------------------- |
| `getEventListeners($('.venue-card__book'))` на старті       | `click: 1`                                     |
| те саме після пошуку «Одеса»                                | `{}` — **немає**                               |
| клік «Забронювати» на Active Hall після пошуку              | `#booking-dialog.open = false`                 |

`renderResults` перезаписує `#results.innerHTML` — старі вузли видаляються, створюються нові, а
`bindBookButtons()` викликається лише раз на старті. Обробник прив'язаний до вузла, тож нові кнопки
його не мають. DOM breakpoint «subtree modifications» на `#results` під час пошуку зупиняє
виконання в `renderResults` (`render.js:29`), викликаному з `handleSearch` після `await` — саме
там вузли карток замінюються.

**Виправлення:** [`181b2a7`](https://github.com/San4o-0/CBHTMLCSS_web/commit/181b2a7) —
`bindBookButtons()` після кожного рендеру результатів пошуку. **Після:** після пошуку «Одеса»
кнопки мають `click: 1`, «Забронювати» на Active Hall відкриває діалог Active Hall.

### Чому DevTools — сильніший доказ, ніж HTML-файл

HTML-файл показує розмітку до виконання JavaScript: у ньому немає жодної картки й жодного
обробника. Дефекти B виникають у **живому** DOM: хто перший серед кнопок header, які вузли
`#results` існують після пошуку, на якому вузлі висить обробник. `getEventListeners`, вкладка Event
Listeners і DOM breakpoints показують стан у момент виконання, а не припущення з читання коду.

## 4. Сценарій C — Event Loop

### C.1. Статус «Знайдено: N» не відповідає карткам

**Очікувано (§3.3):** під час пошуку — «Шукаємо…», після — «Знайдено: N», де N = кількість
показаних карток. **Фактично:** «Шукаємо…» не видно, а N — кількість карток **попереднього**
результату (6 популярних → пошук «Львів + Футбол» дає 1 картку, а статус «Знайдено: 6»; далі
«Одеса» — 2 картки, статус «Знайдено: 1»).

**Фактичний порядок (logpoints у Sources, main.js):**

```text
[1] handleSearch: старт, статус «Шукаємо…»            (main.js:36)
[2] handleSearch: перед await fetchVenues              (main.js:39)
[3] другий обробник submit: results.children = 6      (main.js:49)
[4] handleSearch: після await, рендер 1 карток         (main.js:40)
статус після пошуку: «Знайдено: 6», карток: 1
```

**Пояснення.** Подія `submit` — один task, у якому браузер по черзі викликає обидва обробники.
`handleSearch` — async: виконується **синхронно до першого `await`** ([1], [2]), повертає pending
Promise, і браузер одразу викликає другий обробник [3]. Той рахує `results.children`, поки там ще
старі 6 карток, і затирає «Шукаємо…» значенням «Знайдено: 6». `fetchVenues` чекає на таймер
затримки (Web API → task queue); коли він спрацьовує й Promise виконується, продовження
`handleSearch` потрапляє в microtask queue і лише тоді рендерить нові картки [4] — статус уже ніхто
не оновлює.

```text
click «Знайти» → task «submit»
  Call Stack: handleSearch() — до await → [1] [2] → повертає Promise
              обробник статусу → [3] рахує СТАРІ картки → «Знайдено: 6»
  Web API: setTimeout(400 мс) у fetchVenues
     ↓ (через 400 мс)
  task queue: callback таймера → resolve(…)
  microtask queue: продовження handleSearch після await → [4] renderResults (1 картка)
     (спорожнюється після кожного task, до рендерингу)
```

**Виправлення порядку:** [`9316238`](https://github.com/San4o-0/CBHTMLCSS_web/commit/9316238) —
статус рахується в `handleSearch` **після** `renderResults`, окремий обробник прибрано.
`setTimeout(…, 500)` для статусу не приймається: це ставка на те, що сервер відповість швидше за
500 мс (Київ — 1200 мс), тобто дефект лише рідше проявляється, а «Шукаємо…» так і не показується.

**Після:** «Шукаємо…» + `aria-busy="true"` під час пошуку; «Знайдено: 1» для Львів + Футбол,
«Знайдено: 2» для Одеси, «Нічого не знайдено» для Харків + Волейбол.

### C.1b. Застарілий результат перезаписує останній пошук

**Кроки:** «Київ» → «Знайти», одразу «Львів» → «Знайти». **Фактично до виправлення:** через 0.6 с
показано Львів, через 1.8 с — **Київ** (Arena Sport, Tennis Point, Hoop Point), хоча останнім був
пошук «Львів». Причина — порядок завершення: Promise Києва виконується пізніше (затримка 1200 мс
проти 400 мс), і його продовження рендерить останнім.

**Виправлення:** [`12636b9`](https://github.com/San4o-0/CBHTMLCSS_web/commit/12636b9) — кожен
пошук отримує номер (`++lastSearch`); після `await` відповідь застарілого пошуку не рендериться.
Затримки в `api.js` не змінено. **Після:** і через 0.6 с, і через 1.8 с — Smash Club, Green Field,
Royal Court, «Знайдено: 3».

**Prompt AI:** «Після пошуку статус показує кількість карток попереднього результату, а
"Шукаємо…" не видно. Нижче — handleSearch, другий обробник submit і порядок logpoints. Поясни
порядок виконання через Call Stack, task і microtask queue. Не пропонуй setTimeout. Код не
змінюй». **Відповідь AI (стисло):** «Обидва обробники `submit` виконуються в одному task;
async-функція повертає керування на першому `await`, тому обробник статусу бачить старий DOM.
Статус треба оновлювати після рендеру в тій самій функції. Окремо: при кількох пошуках
продовження після `await` виконуються в порядку відповідей, а не запитів — потрібна перевірка
актуальності запиту».

### C.2. Експеримент: два обробники кліку

| Випадок                                       | Мій прогноз                                                                     | Прогноз AI (до запуску)                                                         | Фактично                                                                        |
| --------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| (а) клік мишею                                | listener 1, listener 2, promise 1, microtask 2, timeout 1                       | listener 1, promise 1, listener 2, microtask 2, timeout 1                       | listener 1, promise 1, listener 2, microtask 2, timeout 1                       |
| (б) `btn.click(); console.log('after click()')` | listener 1, listener 2, promise 1, microtask 2, after click(), timeout 1        | listener 1, listener 2, after click(), promise 1, microtask 2, timeout 1        | listener 1, listener 2, after click(), promise 1, microtask 2, timeout 1        |

**Де мій прогноз хибний:** (а) я вважав, що обидва обробники виконуються підряд, а microtasks —
після них; (б) — що `click()` завершує подію разом із microtasks до наступного рядка.

**Чому порядок різний.** Microtasks виконуються, щойно **Call Stack порожній**. (а) Клік мишею —
task браузера: після першого обробника стек порожній, тому `promise 1` виконується **між**
обробниками, потім `listener 2` і `microtask 2`; `timeout 1` — окремий task наприкінці. (б)
`btn.click()` синхронно викликає обидва обробники **всередині** скрипта Console: стек не порожній,
доки не виконається весь рядок, зокрема `console.log('after click()')`; лише тоді спорожнюється
microtask queue (`promise 1`, `microtask 2`), а таймер — останнім.

## 6. Підсумок

**Де AI скоротив час:** розбір стеку A.1 і пропозиція одразу подивитися `venue` у кадрі
`createCard`, а не в `formatPrice`; помічена різниця `renderBookingsCount` / `renderBookingCount`;
пояснення порядку C.1 через «async-функція синхронна до першого `await`» і підказка про гонку
відповідей C.1b.

**Де відповідь потребувала перевірки в DevTools:** у B.1 AI пропонував також гіпотезу про CSS, яку
відкинуто перевіркою класу `is-open`; у A.1 гіпотезу про неправильне поле для всіх карток
відкинуто тим, що 6 популярних карток рендеряться з цінами.

**Пропозиція AI, що замаскувала б першопричину.** Якщо обмежити агента умовою «виправ помилку лише у
файлі, де вона виявилася» (`format.js`), він пропонує:

```js
export function formatPrice(value) {
  return `${(value ?? 0).toLocaleString('uk-UA')} грн`;
}
```

Console стала б порожньою, але це приховало б помилку в даних: Royal Court показувався б «від 0
грн/год», бронювання — «0 грн», а реальна ціна 1 200 грн втратилася б мовчки. Помилку в ключі
`pricePerhour` ніхто б не помітив, і вона зламала б будь-яке інше місце, яке читає ціну.
Правильне виправлення — у джерелі (`data/venues.json`), де закладено причину.
